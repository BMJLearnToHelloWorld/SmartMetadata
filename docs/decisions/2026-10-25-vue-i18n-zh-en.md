# Product console chrome uses vue-i18n with persisted zh-CN and en-US

- **Status:** Accepted
- **Revisions:** v1 2026-10-25 (initial)
- **Deciders:** Bernie Bai (UI parity batch 1 / Phase A)
- **Guard:** `smartmetadata-ui` AppShell and LoginView strings come from `src/i18n/locales/{en-US,zh-CN}.ts`; locale preference is `sm.locale.v1`; reviewers reject hard-coded chrome copy and CCL React locale JSON reuse
- **Related:** `docs/rebuild/UI_PARITY_BATCH1.md`; ADR:2026-10-22-clean-room-vue-spa

## Context

The Phase 1 Vue shell mixed English labels with no locale switch. Official
OpenMetadata chrome is i18n-backed (CCL React). Batch 1 authorized a clean-room
zh-CN / en-US switcher on the rebuilt console only.

## Decision

- Add **vue-i18n** (MIT) in composition mode. Catalogs live in
  `smartmetadata-ui/src/i18n/locales/`. Do not import
  `openmetadata-ui/.../locale/languages/*.json`.
- Supported locales: `en-US`, `zh-CN`. Storage key `sm.locale.v1`. Stored
  value wins; otherwise a `zh*` browser language maps to `zh-CN`, else
  `en-US`.
- Wire Ant Design Vue `ConfigProvider` locale to the same choice.
- This record covers **shell, nav, and login** strings. Page-body copy on
  Explore/asset and other CRUD views is a later batch.

## Consequences

Chrome is bilingual without copying CCL locale files. Adding a third locale,
translating inner pages, or changing the storage key is a new decision.
